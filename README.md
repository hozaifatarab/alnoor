# نظام إدارة المؤسسة التعليمية

نظام إدارة متكامل لمؤسسة تعليمية عربية (RTL) مبني بـ **PyWebIO 1.8.4** بمعمارية طبقية
واختبارات آلية — بلا HTML/JS مكتوب يدوياً.

> **حالة المشروع:** المرحلة 2 (الحضور بـ QR والدرجات) مكتملة ومُختبَرة.
> المرحلة 3 = المالية والتقارير والتقسية.

## 5) المعمارية الطبقية

```
pages/        واجهة PyWebIO فقط (تجميع مكوّنات + استدعاء الخدمات)   ← لا SQL ولا قواعد أعمال
ui/           الثيم RTL، التخطيط، المكوّنات (جداول/نماذج/تأكيد)، الرسوم، مولّدات الخيارات
core/services  منطق الأعمال والقواعد + التحقق + التدقيق              ← بلا أي استدعاء للواجهة
core/repos     مستودعات SQL بمعاملات (parameterized)                 ← لا منطق أعمال
core/db.py     اتصال، معاملات، هجرات مرقّمة (forward-only)
```

قواعد ملزمة في المشروع:
* لا استعلام SQL خارج `core/repos`، ولا `pywebio.output` داخل `core/services` → قابلة للاختبار بالكامل.
* كل عملية حساسة تُسجَّل في `audit_log` مع المستخدم وعنوان IP.
* الهجرات في `core/migrations/*.sql` مرقّمة ولا تُعدَّل بعد التطبيق (تُضاف هجرة جديدة).
* فهارس على الأعمدة الساخنة، `PRAGMA foreign_keys=ON`، وضع WAL، وقيود `CHECK/UNIQUE` على مستوى القاعدة.
* كلمات المرور: PBKDF2-HMAC-SHA256 (200,000 تكرار + ملح عشوائي لكل مستخدم) ومقارنة زمنية ثابتة.
* قفل الحساب تلقائياً بعد 5 محاولات فاشلة لمدة 15 دقيقة + إلزام تغيير كلمة المرور المؤقتة.

## 6) الاختبارات

### النسخ الاحتياطي والاستعادة

```bat
python tools\backup_db.py backup
python tools\backup_db.py backup D:\backups\school.instdb
python tools\backup_db.py restore D:\backups\school.instdb
```

تُنشأ النسخ متسقة ومشفّرة بـ AES-GCM، وتُطلب عبارة مرور لا تقل عن 12 حرفاً دون إظهارها في الطرفية. لا يمكن استبدال ملف نسخة موجود. أوقف التطبيق قبل الاستعادة؛ تُفحص سلامة الملف أولاً وتُنشأ نسخة مشفّرة من القاعدة الحالية تلقائياً قبل الاستبدال. احتفظ بعبارة المرور، فلا يمكن استعادة النسخة من دونها.

```bat
tools\run_tests.bat                          :: تشغيل كامل مع تقرير في data\testrun.log
python -m unittest discover -s tests -t .    :: مباشرة
python tools\check_env.py                    :: فحص البيئة وتوفر واجهات PyWebIO
```

### قرارات تصميم الحضور بـ QR (جاهزة للتنفيذ)
* إصدار البطاقات من شاشة المدير فقط: `/?app=student_cards`.
* حمولة البطاقة: `STD|السنة|رقم الطالب|<توقيع HMAC-SHA256 بطول 128 بت>` والسرّ في `settings.qr_secret` (قابل للتدوير من شاشة الإعدادات). بيانات QR مقروءة عند المسح؛ التوقيع ليس سرّاً، بل يمنع إنشاء رمز مزوّر دون مفتاح النظام.
* الكاميرا لا تقبل إلا توقيع 128 بت. الأرقام الخام مسموحة فقط في مسار الإدخال اليدوي/قارئ USB كبديل تشغيلي، ولا تُعدّ إثباتاً لصحة بطاقة QR. يجب إعادة إصدار البطاقات القديمة ذات التوقيع الأقصر قبل استخدامها.
* المسار الأساسي: المعلم/المشرف يمسح بطاقة كل طالب بكاميرا جهازه، مع بدائل إلزامية (إدخال يدوي/قارئ باركود USB/«الكل حاضر»).
* الجسر التقني: `eval_js` مع Promise + نبضة إيقاف كل 15 ثانية، ومنطق العمل في خدمة نقية قابلة للاختبار.
* **قيد معروف:** كاميرا المتصفح تعمل فقط في سياق آمن (`localhost` أو HTTPS)؛ لذا ستُضاف خدمة تشغيل بـ HTTPS
  (شهادة ذاتية) مع إبقاء البدائل اليدوية متاحة دائماً.
